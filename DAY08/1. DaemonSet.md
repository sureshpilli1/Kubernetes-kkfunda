**DaemonSet - Complete Guide KK FUNDA**
1. What is a DaemonSet?**
A **DaemonSet** ensures that **one copy of a Pod runs on every node** in the Kubernetes cluster.
So whenever:
* A new node joins → Pod is automatically created on that node.
* A node is removed → Pod is automatically removed.
Why this is needed?

Some workloads are **node-specific** and must run everywhere, such as:

| Use Case                                             | Purpose                        |
| ---------------------------------------------------- | ------------------------------ |
| **Log collectors** (Fluentd, Filebeat)               | Collect logs from each node    |
| **Monitoring agents** (Node Exporter, Datadog agent) | Collect node-level metrics     |
| **Security agents**                                  | Enforce policies on each node  |
| **Kube-proxy / network plugins**                     | Manage networking on each node |

---

## **2. How DaemonSet Works Internally**

| Component                     | Responsibility                                    |
| ----------------------------- | ------------------------------------------------- |
| `DaemonSet Controller`        | Watches nodes and ensures Pods exist on all nodes |
| `Node Selector / Tolerations` | Controls where Pods can run                       |
| `Template.spec`               | Defines the container specification               |

DaemonSet is **similar to Deployment**, except:

* **Deployment** tries to maintain a fixed replica count (e.g., 3 Pods).
* **DaemonSet** runs **1 Pod per node** (not fixed count).

3. Real-Time Example: Node Exporter (Monitoring Agent)**
**Objective**
Deploy **node-exporter** on **every node** to collect CPU, RAM, Disk metrics.
**YAML File: `node-exporter-daemonset.yaml`**

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: kube-system
spec:
  selector:
    matchLabels:
      app: node-exporter
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      hostNetwork: true
      hostPID: true
      containers:
      - name: node-exporter
        image: prom/node-exporter:latest
        ports:
        - containerPort: 9100
          name: metrics
```

**Key Points**

| Field                 | Meaning                                                          |
| --------------------- | ---------------------------------------------------------------- |
| `hostNetwork: true`   | The Pod shares the node network → metrics accessible via node IP |
| `hostPID: true`       | Allows access to host process namespace                          |
| `containerPort: 9100` | Port where metrics are exposed                                   |

---

4. Apply the DaemonSet**

```bash
kubectl apply -f node-exporter-daemonset.yaml
```

5. Validate DaemonSet**
**Check DaemonSet**

```bash
kubectl get daemonset -n kube-system
```
Expected Output:

```

```

> `DESIRED = number of nodes in your cluster`

Pick any node IP & test:

```bash

```

**7. (Optional) Expose via Service (for Prometheus)**


**8. Troubleshooting**

| Issue                             | Reason                         | Fix                                                                |
| --------------------------------- | ------------------------------ | ------------------------------------------------------------------ |
| Pods running only on worker nodes | Schedulable master disabled    | `kubectl taint node master node-role.kubernetes.io/control-plane-` |
| Pod not starting                  | Image pull issue               | Check image URL / registry access                                  |
| Metrics not showing               | Firewall / firewallD blocking  | Allow port `9100` on each node                                     |
| Port conflicts                    | Something else using port 9100 | Change container port                                              |

**9. When to Use Deployment Instead of DaemonSet**

Use **Deployment** when:

* The app is **not tied to nodes**
* You just need a **fixed number of replicas**
* You want **rolling updates / autoscaling**

Use **DaemonSet** when:

* Workload must run **on every node**
* Workload needs **host-level access




NOTES FROM BLOG:


1. Introduction
In Kubernetes, different controllers manage how Pods are scheduled and maintained across the cluster.
One of the most specialized and powerful among them is the DaemonSet—designed to ensure that a specific Pod runs on every Node, or on a targeted subset of Nodes.
This is very useful for background system tasks that should always be present on all Nodes, such as log collectors, monitoring agents, or networking services.

2. What Is a DaemonSet?
A DaemonSet makes sure that one Pod runs on every Node in the cluster or only on selected Nodes. It’s perfect for background services that need to be available everywhere.
Key Features of DaemonSets
1. One Pod per Node
A DaemonSet ensures that exactly one Pod runs on each Node.
This is different from a Deployment, which spreads Pods randomly across the cluster.

2. Automatic Pod Management
When a new Node joins the cluster, the DaemonSet automatically schedules a Pod on it.
When a Node is removed, the associated Pod is deleted automatically.
No manual scaling is required.

3. Selective Node Deployment
You don’t always need DaemonSets on all Nodes. Kubernetes lets you control where DaemonSet Pods should run using:
Node Selectors – match Pods to Nodes with specific labels.
Affinity Rules – more flexible conditions for Node placement.
Taints and Tolerations – allow Pods to run even on “restricted” Nodes (like masters).

3. Common Use Cases of DaemonSet
DaemonSets are ideal for workloads that need to run on every Node in a Kubernetes cluster.
These are typically system-level services that provide observability, connectivity, or infrastructure support. Let’s explore the most common scenarios:

1. Monitoring
Deploy agents like Prometheus Node Exporter or Datadog Agent to collect Node-level metrics.
These agents need to run on every Node to gather complete metrics across the cluster.
DaemonSet ensures automatic deployment of one agent Pod per Node, including any new Nodes that join later.

2. Logging
Run log collectors like Fluentd, Logstash, or Filebeat to gather logs from all Nodes.
Log collectors gather logs from containers and system processes, then forward them to centralized logging platforms for analysis and storage.
Logs are stored locally on each Node, so collectors must run on each Node to access and ship them.
DaemonSet ensures consistent log collection across the entire cluster without manual scaling.

3. Networking Services
These services manage networking between Pods, Nodes, and external systems. They often handle routing, DNS, or network policy enforcement.
kube-proxy (manages network rules for services)
CNI plugins (like Calico, Flannel, or Weave Net)
VPN clients (for secure Node-to-Node or Node-to-cloud communication)
Networking components must be present on every Node to ensure consistent connectivity and policy enforcement.
DaemonSet guarantees that each Node has the necessary networking tools running locally.

4. Understanding DaemonSet Pods in the Cluster
When you run:
kubectl get all -A -o wide
You see many system Pods running inside the cluster, especially in the kube-system namespace.
Some Pods run only on the Master Node, while others run on all Nodes (Master + Workers).
This difference is the key to understanding DaemonSets.

1. Pods Running in the Cluster
From the output, you can notice Pods like:
coredns
etcd
kube-apiserver
kube-controller-manager

2. Control Plane Pods (Run Only on Master Node)
Components like:
etcd

These are control plane components.
They only run on the Master Node (ip-172-31-34-191).
They don’t need to run on worker nodes.

3. DaemonSet Pods (Run on All Nodes)
Some Pods like:
kube-proxy

These are deployed as DaemonSets, so you see them on every Node:

kube-proxy runs on ip-172-31-34-191, ip-172-31-5-194, ip-172-31-3-215
weave-net also runs on ip-172-31-34-191, ip-172-31-5-194, ip-172-31-3-215
Exactly one Pod per Node that’s how DaemonSets work.
This proves DaemonSet ensures coverage across the whole cluster.

4. Key Point
Some Pods are only on Master Node (ip-172-31-34-191) → e.g., etcd, apiserver.
Some Pods are on all Nodes (Master + Workers) → e.g., kube-proxy, weave-net.
This shows the difference in how controllers (ReplicaSet, Deployment, DaemonSet) manage Pods.

Short Summary
DaemonSet =

✔ Used for system-level components

✔ N replicas
✔ Used for applications


5. Basic DaemonSet
Step 1: Create Basic DaemonSet
This example runs nginx on all worker Nodes (not master/control-plane).
You don’t set replicas manually; the Pod count always equals the Node count.
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: nginx
spec:
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx
        ports:
        - containerPort: 80

kubectl apply -f ds.yaml

6. Deploy DaemonSet on Master Node also
First delete old DS:
kubectl delete -f ds.yaml
ubuntu@ip-172-31-34-191:~$ kubectl delete -f ds.yaml
daemonset.apps "nginx" deleted
Now apply updated DS with tolerations:
If you also want Pods on master/control-plane Nodes, you need to add tolerations in the Pod spec to allow scheduling on tainted Nodes.
DaemonSet – Kubernetes Official Docs
key: node-role.kubernetes.io/control-plane
operator: Exists
effect: NoSchedule

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: nginx
spec:
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      tolerations:
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: nginx
        image: nginx
        ports:
        - containerPort: 80


Here, the toleration overrides the master Node's NoSchedule taint, allowing the Pod to run on it too.

Now 3 Pods → one on each Node (Master + 2 Workers).
Without tolerations → DaemonSet Pods run only on Worker Nodes.
With tolerations → DaemonSet Pods run on all Nodes including Master.

7. Key Takeaways
DaemonSet = One Pod per Node, automatically managed by Kubernetes.
Best suited for system-level tasks like monitoring, logging, or networking.
Doesn’t run on master Nodes by default → you need tolerations to include them.

Unlike Deployments, you don’t set replicas manually; the Pod count always equals the Node count.
