1. Why do we need ConfigMaps & Secrets?
Imagine your app needs:
DB host → mongosvc
DB username → devdb
DB password → devdb@123
Hardcoding inside image → bad practice
Editing code for every environment → messy
Kubernetes solution:
Configuration is stored OUTSIDE the container



2. What is a ConfigMap?
A ConfigMap is:
A Kubernetes object used to store non-sensitive configuration data as key-value pairs
A ConfigMap is an API object used to store non-confidential data in key-value pairs. 
ConfigMap = keep application configuration separate from your application image/code.
Pods can consume ConfigMaps as environment variables, command-line arguments, or as configuration files in a volume.
Caution:
--------
ConfigMap does not provide secrecy or encryption. If the data you want to store are confidential, use a Secret rather than a ConfigMap, 
or use additional (third party) tools to keep your data private.

Example use cases
App settings
URLs
Feature flags
Port numbers
File-based configs

| Configuration      | Example                    | What it controls                 |
| ------------------ | -------------------------- | -------------------------------- |
| App settings       | `ENVIRONMENT=dev`          | Application behavior/settings    |
| URLs               | `PAYMENT_URL=...`          | Where another service is located |
| Feature flags      | `NEW_PAYMENT_FEATURE=true` | Enable/disable features          |
| Port numbers       | `SERVER_PORT=8080`         | Application's listening port     |
| File-based configs | `application.properties`   | Configuration provided as a file |

1. application settings:
---------------------
Application settings are simply configuration values that tell an application how it should behave or operate.
"Values that control how my application runs, without changing my application code or rebuilding my Docker image."

| Setting       | Meaning                                                      |
| ------------- | ------------------------------------------------------------ |
| `ENVIRONMENT` | Tells the application which environment it is running in     |
| `LOG_LEVEL`   | Controls how much information the application writes to logs |
| `SERVER_PORT` | Tells the application which port it should listen on         |

For example:
LOG_LEVEL = INFO
means the application might show:
INFO Application started
INFO Database connected
If you change it to:
LOG_LEVEL = DEBUG
the application may produce much more detailed information.

2. URLs:
----------
Suppose your Spring Boot application needs to communicate with another application.

For example:
Payment Service URL:
http://payment-service:8080
Instead of hardcoding this inside your application:
String url = "http://payment-service:8080";
you can put it in a ConfigMap:
data:
  PAYMENT_URL: "http://payment-service:8080"
Then your application reads:
PAYMENT_URL
      ↓
http://payment-service:8080

This is particularly useful because the URL might change between environments.
Development:
http://payment-dev:8080
QA:
http://payment-qa:8080
Production:
http://payment-prod:8080
The application code doesn't need to change.

You can use that same image in all three environments:

                 spring-app:1.0
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        DEV           QA           PROD
          │            │            │
          ▼            ▼            ▼
      ConfigMap    ConfigMap    ConfigMap
          │            │            │
          ▼            ▼            ▼
   payment-dev   payment-qa   payment-prod

The application code/image remains the same.
Only the configuration value changes.

3. Feature flags
A feature flag is a configuration value that controls whether a feature is enabled or disabled.
For example:
data:
  NEW_PAYMENT_FEATURE: "true"
Your application might behave like:
NEW_PAYMENT_FEATURE = true
        ↓
New payment feature enabled

If:
data:
  NEW_PAYMENT_FEATURE: "false"
then:
New payment feature disabled
This is useful when you want to turn features on/off without rebuilding the Docker image.

For example:
Production
    ↓
NEW_PAYMENT_FEATURE=false

Later:
NEW_PAYMENT_FEATURE=true
The application can use that configuration.

4. Port numbers
Suppose your application listens on port:
8080
You could have:
data:
  SERVER_PORT: "8080"
Your application reads:
SERVER_PORT=8080
Spring Boot can use this as:
server.port=${SERVER_PORT}
Now the same application can run on different ports:
Dev  → 8080
QA   → 8081
Prod → 9090
without changing the application code.
Important distinction
A ConfigMap containing:
SERVER_PORT: "8080"
doesn't itself open a Kubernetes network port.
It only provides the configuration value to the application.
Kubernetes Service is what provides networking/exposure between Pods.

5. File-based configurations
A ConfigMap doesn't have to be used only as environment variables.
It can also provide a file to your container.
For example:
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  application.properties: |
    server.port=8080
    logging.level.root=INFO

Now you can mount the ConfigMap as a volume.

volumes:
  - name: config-volume
    configMap:
      name: app-config
and:
volumeMounts:
  - name: config-volume
    mountPath: /config

Inside the container you could get:
/config/application.properties
So the flow becomes:
ConfigMap
     │
     │ application.properties
     ▼
Pod volume
     │
     ▼
Container
     │
     ▼
/config/application.properties

This is called a file-based configuration.










Example ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: mongosvc
  DB_PORT: "27017"
  APP_MODE: production

examples from notes:

apiVersion: v1
kind: ConfigMap
metadata:
  name: game-demo
data:
  # property-like keys; each key maps to a simple value
  player_initial_lives: "3"
  ui_properties_file_name: "user-interface.properties"

  # file-like keys
  game.properties: |
    enemy.types=aliens,monsters
    player.maximum-lives=5
  user-interface.properties: |
    color.good=purple
    color.bad=yellow
    allow.textmode=true
---
apiVersion: v1
kind: Pod
metadata:
  name: configmap-demo-pod
spec:
  containers:
    - name: demo
      image: alpine
      command: ["sleep", "3600"]
      env:
        # Define the environment variable
        - name: PLAYER_INITIAL_LIVES # Notice that the case is different here
                                     # from the key name in the ConfigMap.
          valueFrom:
            configMapKeyRef:
              name: game-demo           # The ConfigMap this value comes from.
              key: player_initial_lives # The key to fetch.
        - name: UI_PROPERTIES_FILE_NAME
          valueFrom:
            configMapKeyRef:
              name: game-demo
              key: ui_properties_file_name
      volumeMounts:
      - name: config
        mountPath: "/config"
        readOnly: true
  volumes:               # You set volumes at the Pod level, then mount them into containers inside that Pod
  - name: config
    configMap:           # Provide the name of the ConfigMap you want to mount.
      name: game-demo    # An array of keys from the ConfigMap to create as files
      items:
      - key: "game.properties"
        path: "game.properties"
      - key: "user-interface.properties"
        path: "user-interface.properties"



kubectl exec -it configmap-demo-pod  -- env  --> to see the env details

kubectl describe po configmap-demo-pod --> see the volume details as configConfig

kubectl exec -it configmap-demo-pod -- ls /config


kubectl exec -it configmap-demo-pod -- cat /config/game.properties

kubectl exec -it configmap-demo-pod -- cat /config/user-interface.properties

3. What is a Secret?
A Secret is:
A Kubernetes object used to store sensitive data
Example use cases
Passwords
API keys
Tokens
Certificates
Example Secret
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
data:
  DB_USERNAME: ZGV2ZGI=        # base64(devdb)
  DB_PASSWORD: ZGV2ZGJAMTIz    # base64(devdb@123)

Note:
Values must be base64 encoded





Secret = information that your application needs but you don't want to keep as ordinary configuration.
Let's understand each one.
1. Passwords
Suppose your MongoDB has:
Username: devdb
Password: devdb@123
The password should not normally be written directly in your Deployment:
env:
  - name: MONGO_DB_PASSWORD
    value: devdb@123
Instead, create a Secret:

apiVersion: v1
kind: Secret
metadata:
  name: mongodb-secret
type: Opaque
stringData:
  username: devdb
  password: devdb@123

Then your Spring Boot Pod can get the password from the Secret.
Conceptually:
Secret
  │
  └── password = devdb@123
          │
          ▼
   Spring Boot container
          │
          ▼
      MongoDB

This is exactly related to your previous MongoDB example.

2. API keys
An API key is a credential that an application uses to access another service.
For example, suppose your application uses a weather service:
Weather API
     ↑
     │ API key
     │
Spring Boot

You might receive a key such as:
API_KEY = abc123xyz
You shouldn't put that directly into your Java code:
String apiKey = "abc123xyz";
Instead, store it in a Secret:
stringData:
  WEATHER_API_KEY: "abc123xyz"
Then your application reads the key from the Secret.

3. Tokens
A token is another type of credential used to authenticate or authorize access.
For example, your application might need an access token:
TOKEN = eyJhbGciOi...
Instead of:
Java code
    ↓
token written directly in code
you can have:
Kubernetes Secret
       ↓
TOKEN
       ↓
Spring Boot

The application can then use the token when communicating with another system.
Examples include:
OAuth access tokens
Service authentication tokens
Personal access tokens
Application authentication tokens

4. Certificates
Certificates are also commonly stored/provided using Secrets.
For example, suppose your application needs HTTPS.
You might have:
server.crt
server.key
The private key is particularly sensitive.
A Kubernetes Secret can contain these files:

apiVersion: v1
kind: Secret
metadata:
  name: tls-secret
type: kubernetes.io/tls
data:
  tls.crt: ...
  tls.key: ...

Then Kubernetes can make those certificate files available to a Pod.
Conceptually:
Secret
 ├── server certificate
 └── private key
        │
        ▼
      Pod
        │
        ▼
      HTTPS



4. Key difference (VERY IMPORTANT)
| Feature   | ConfigMap     | Secret      |
| --------- | ------------- | ----------- |
| Data type | Non-sensitive | Sensitive   |
| Encoding  | Plain text    | Base64      |
| Security  | Less secure   | More secure |
| Use case  | Config        | Credentials |


5. How to USE them in Pods
You can use both in 2 ways:
Method 1: As Environment Variables
Using ConfigMap
env:
- name: DB_HOST
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: DB_HOST
Using Secret
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: app-secret
      key: DB_PASSWORD
Shortcut (import all values)
envFrom:
- configMapRef:
    name: app-config
- secretRef:
    name: app-secret

6. Method 2: As Files (VERY POWERFUL)
ConfigMap as volume
volumes:
- name: config-vol
  configMap:
    name: app-config
Mount in container
volumeMounts:
- name: config-vol
  mountPath: /etc/config

Inside container:

/etc/config/DB_HOST
/etc/config/APP_MODE
Secret as volume
volumes:
- name: secret-vol
  secret:
    secretName: app-secret

7. Full real-world example (your style)
containers:
- name: springapp
  image: myapp

  envFrom:
  - configMapRef:
      name: app-config
  - secretRef:
      name: app-secret

Your app automatically gets:

DB_HOST
DB_PORT
DB_USERNAME
DB_PASSWORD

8. How this fits with your MongoDB example
Instead of:
env:
- name: MONGO_DB_USERNAME
  value: devdb
Better:
env:
- name: MONGO_DB_USERNAME
  valueFrom:
    secretKeyRef:
      name: app-secret
      key: DB_USERNAME

9. Important rules
ConfigMap
Use for non-sensitive data
Easy to edit without rebuilding image
Secret
Use for passwords & credentials
Base64 encoded (not encrypted by default )

10. Common mistakes
Storing passwords in ConfigMap
Hardcoding secrets in YAML
Forgetting base64 encoding
Mixing up key names

11. Simple mental model
ConfigMap = App settings
Secret = App passwords
Final summary
ConfigMap → non-sensitive config
Secret → sensitive data
Both can be used as:
Environment variables
Mounted files (volumes)

what is an API:
---------------
API stands for Application Programming Interface.
An API is a way for one software application to communicate with another software application.
API is a defined way for one application to request data or functionality from another application.
"API key", A credential used by an application when accessing an API.

Suppose you have a Spring Boot application.
Your application needs payment functionality.
You don't want to build the entire payment system yourself.
Instead, you use a payment provider's API.
Your Spring Boot application sends:
"Please process ₹500 payment."
to the payment provider's API.
The payment service processes it and sends back:
"Payment successful."
So:
Spring Boot Application
          │
          │ API request
          ▼
    Payment API
          │
          ▼
   Payment System
          │
          │ API response
          ▼
Spring Boot Application
