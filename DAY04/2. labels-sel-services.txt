NOTES FROM BLOG:

1. Labels
A label is just a key/value pair attached to a Kubernetes object (like Pod, Service, Deployment, etc.).
Labels are used for categorization and organization.
You can create your own labels and apply them to any object.
Example:
labels:
  app: javawebapp
  environment: production

2. Selectors
A selector is used to find objects by their labels. It’s like Filter, Conditions and query to your labels
Services, ReplicaSets, and Deployments use selectors to decide which Pods they should work with.
Example:
selector:
  app: javawebapp

3. Why Are They Important?
1.Labels and selectors are crucial for creating Services.
2.They make sure traffic is routed to the right Pods. This way, Kubernetes knows which Pods should receive the traffic.
3.Without labels, services cannot find Pods → traffic will break.
4.By grouping Pods with labels, you can easily manage environments (dev, test, prod).
Simple workflow:
Add labels to Pods.
Create a Service with a selector.
Kubernetes automatically routes traffic from the Service → to the Pods with matching labels.

4. How Do Labels Form Groups?
Think of labels as group tags:
If multiple Pods have app: javawebapp, they form one group.
If some Pods have environment: production, they form the “production” group.
This way you can create logical groups across your cluster.

5. What If Labels Were Missing?
No Service Creation → Services wouldn’t know which Pods to connect to.
Broken Routing → Traffic wouldn’t reach the right Pods.
Chaos → Hard to organize or manage different apps and environments.
In short: labels are essential for Kubernetes to function smoothly.

15. Service in Kubernetes
A Service in Kubernetes provides a stable way for communication between Pods, ensuring availability and proper traffic routing. 
Since Pods are dynamic (they can restart and change IPs), Services act as a stable entry point.

16. Why Services Need Labels
Labels are key-value pairs attached to Pods.
A Service uses selectors to find which Pods it should route traffic to.
Without labels, Services cannot identify Pods.
Kubernetes automatically creates an Endpoint object for each Service, storing the IP addresses and ports of the matching Pods.

17. Endpoints
Endpoints contain network information (Pod IPs + Ports).
They ensure that traffic from the Service is always routed to the correct Pods.
If Pods change, Endpoints are updated automatically.

18. Types of Kubernetes Services
ClusterIP
NodePort
LoadBalancer
ExternalName
1. ClusterIP Service (Default)
Default and most common service type.
Kubernetes assigns a cluster-internal IP address to the Service.
Accessible only within the cluster.
Optional: you can set clusterIP in the service YAML.
Not accessible from outside the cluster unless exposed with NodePort/LoadBalancer/Ingress.
Flow:
Pod → Label → Service → Endpoint → Traffic Routing

2. NodePort
Exposes the Service on a static port (range: 30000–32767) on each node’s IP.
Useful for basic external access (but not ideal for production).
Extension of ClusterIP.
Accessible using <NodeIP>:<NodePort>.
Each Node proxies the traffic to the Service → Pods.
Use Cases
When you want external connectivity without cloud load balancer.
Useful for testing / small setups.
Can put your own load balancer above the nodes.
Example: Java Web App Pod + NodePort Service
apiVersion: v1
kind: Pod
metadata:
  name: javawebapp-nodeport
  namespace: test-ns
  labels:
    app: java
spec:
  containers:
    - name: javawebapp1
      image: kkeducationb2/java-webapp:1.1
      ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: javawebapp-nodeport-service
  namespace: test-ns
spec:
  selector:
    app: java        # Must match Pod label
  ports:
    - port: 8080     # ClusterIP service port
      targetPort: 8080   # Pod container port
      nodePort: 30080    # NodePort (must be 30000–32767 if specified)
  type: NodePort

Relationship Between Label & Selector
Pod label = app: java
Service selector = app: java
Because they match, the Service discovers the Pod and creates an Endpoint to forward traffic.

3. LoadBalancer
Extension of NodePort.
Integrates with cloud provider’s load balancer (AWS ELB, GCP LB, Azure LB).
Exposes service to the internet with public IP.
Mostly used in production deployments.
The cloud load balancer automatically routes traffic → Service → Pods.
Use Cases
Production-grade external exposure.
When running Kubernetes on cloud providers.

4. ExternalName
Maps a Service to an external DNS name instead of Pod IPs.
No selectors, no proxying.
Returns a CNAME record to redirect traffic.
Use Cases
Connect Kubernetes Pods to external databases/services.
