ReplicaSet
==========

--> ReplicaSet is the next-generation Replication Controller.

--> The only difference between a ReplicaSet and a Replication Controller right now is the selector support.

ReplicaSet supports the new set-based selector  requirements as described in the labels user  guide whereas a Replication Controller only  supports equality-based selector requirements.



k8s RepicationController
========================

equality based selector
-----------------------

<key>: <value>

app: javawebapp


k8s ReplicaSet
===============

equality based selector
-----------------------

<key>: <value>

app: javawebapp

set based selectors
--------------------

key in(value1,value2)

key not in(value1,value2)




--> RC selector is an optional , in RS selector is mandatory.






Syntax
======

apiVersion: apps/v1
kind: ReplicaSet
metadata:
 name: <RS-Name>
 namespace: <NS>
spec:
 replicas: 3
 selector:
 	matchLabels:
 	  <key>: <value>
 	MatchExpressions:
 	 - key: <key>
 	   operators: <in / not in>
 	   values:
 	   - <value1>
 	   - <value2>
 	template:
 		metadata: 
 			name: <pod-Name>
 			labels:
 			  <key> : <value>
 	    spec:  
 	     containers:
 	     	- name: <containerName>
 	     	  image: <image-details>
 	     	  ports:
 	     	  - containerPort: <CP>
---

========

BLOG NOTES:


1. What Is a ReplicaSet?

A ReplicaSet (RS) is a Kubernetes object whose main job is:
“Always keep the desired number of Pods running in the cluster.”

How It Works:

You define .spec.replicas (e.g., 3).

RS ensures exactly 3 Pods with matching labels are running.

If a Pod crashes or is deleted → RS creates a new one.

If extra Pods appear → RS deletes them.

Features of ReplicaSet

Self-healing: Crashed or deleted Pods are recreated.

Prevents extra Pods: If more Pods exist than required, ReplicaSet deletes them.

Label-based management: Pods are tracked by labels, not by name.

Advanced selectors: Can use matchLabels (simple) or matchExpressions (advanced).

Deployment integration: Deployments use ReplicaSets internally to manage rolling updates.

2. Desired vs Observed State

This is the heart of Kubernetes controllers.

Desired state: How many Pods you want (e.g., 3).

Observed state: How many Pods are currently running with the correct labels.

RS constantly compares these two and adjusts the number of Pods to match your desired state.

ReplicaSet continuously compares these states:

If the observed count is less than the desired count, it creates new Pods until both match.

If the observed count is greater than the desired count, it deletes the extra Pods.

If the observed count equals the desired count, it does nothing.

This continuous loop is what gives ReplicaSet its self-healing power.

3. How ReplicaSet Uses Label Selectors

ReplicaSet doesn’t care about Pod names. Instead, it uses labels to decide which Pods to manage.

There are two types of selectors:

(a) matchLabels (Equality-based)

The simplest form → just key-value matching.

selector:
  matchLabels:
    app: myapp


This means the ReplicaSet will only control Pods that have app=myapp.

If a Pod doesn’t have this label, RS will ignore it completely.

(b) matchExpressions (Set-based, Advanced)

In Kubernetes, a Pod usually has multiple labels, for example:

labels:
  env: prod
  tier: frontend
  app: myapp


A ReplicaSet uses selectors to decide which Pods it should manage. For simple checks, you can use matchLabels.

But for more complex conditions, you use matchExpressions.

matchExpressions allows you to define conditions such as:

A label’s value must be in a set.

A label’s value must not be in a set.

A label key must exist.

A label key must not exist.

Example with matchLabels + matchExpressions

selector:
  matchLabels:
    env: prod
  matchExpressions:
    - key: tier
      operator: In
      values:
        - frontend
        - backend

Explanation:

The Pod must have env=prod.

The Pod must also have a label tier, and its value must be either frontend or backend.

So, the ReplicaSet will only manage Pods that satisfy both conditions together.

4. Operators in matchExpressions

Let’s look at each operator with examples:

1. In
- key: app
  operator: In
  values:
    - nginx
    - apache


Pod must have the label app, and its value must be either nginx or apache.

2. NotIn
- key: app
  operator: NotIn
  values:
    - mysql


Pod must have the label app, but its value must not be mysql.

3. Exists
- key: release
  operator: Exists


Pod must have a label with the key release. The value does not matter as long as the label key exists.

4. DoesNotExist
- key: debug
  operator: DoesNotExist


Pod must not have the label debug.

matchLabels simple key=value matching.

matchExpressions advanced set-based matching with operators
(In, NotIn, Exists, DoesNotExist).

You can use both together in a ReplicaSet for precise Pod selection.

This makes matchExpressions very powerful, allowing you to finely control which Pods a ReplicaSet manages.

5. Difference Between RC and RS Selector
ReplicationController (RC)

Selector is optional If you don’t give a selector, RC will automatically use the labels from the Pod template.

ReplicaSet (RS)

Selector is mandatory You must define a selector explicitly, otherwise RS won’t know which Pods to manage.

That’s why in RS, your Pod template labels must match the selector. Otherwise, RS will create Pods but won’t track them.

6. ReplicaSet with Service Example

Here’s a real-world YAML where we create a ReplicaSet + Service to expose it:

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: javawebapprs
spec:
  replicas: 2
  selector:
    matchLabels:
      app: javawebapp
  template:
    metadata:
      labels:
        app: javawebapp
    spec:
      containers:
        - name: javawebapp
          image: kkeducation12345/spring-app:1.0.0
          ports:
            - containerPort: 8080

Understanding spec in ReplicaSet

A ReplicaSet YAML also has two spec sections:

1. Outer spec → belongs to the ReplicaSet

This defines how the ReplicaSet behaves.

replicas: 2 → Tells RS to always keep 2 Pods running.

selector → Defines which Pods the RS should manage (based on labels).

template → Provides the Pod definition for new Pods RS creates.

The outer spec controls how many Pods should run and which Pods are managed.

2. Inner spec → belongs to the Pod template

This part describes the Pod itself:

Metadata (labels) → Required for RS to track the Pods.

Containers → What runs inside the Pod (name, image, ports).

The inner spec defines what each Pod looks like.

3. Why selector Is Crucial in RS
selector:
  matchLabels:
    app: javawebapp


This tells RS: “Manage only the Pods that have the label app=javawebapp.”

RS does not look at Pod names, only labels.

If Pods don’t have this label, RS won’t manage them (even if it created them).

4. Common Mistake: Missing Labels in Pod Template

Wrong Example (missing labels):

template:
  metadata:
    # Labels missing here


RS will create Pods but won’t recognize them later, because it only uses labels for tracking.

5. Correct Way: Add Matching Labels
template:
  metadata:
    labels:
      app: javawebapp


Now RS knows these Pods belong to it.

Ensures Pods are tracked properly.

Keeps the Pod count at the desired level.

Enables self-healing (recreates if a Pod crashes).

7. Working with ReplicaSets
(1) Create & Inspect
kubectl apply -f rs.yaml
kubectl get rs

replicaset.apps/javawebapprs created

kubectl get rs

NAME           DESIRED   CURRENT   READY   AGE
javawebapprs   2         2         2       18s

kubectl get all


kubectl get all Shows all common resources in the cluster.

kubectl get all

NAME                        READY   STATUS    RESTARTS   AGE
pod/javawebapprs-abc12      1/1     Running   0          7s
pod/javawebapprs-def34      1/1     Running   0          7s

NAME                        DESIRED   CURRENT   READY   AGE
replicaset.apps/javawebapprs   2         2         2     7s


Here, 2 Pods are running.

Their names start with javawebapprs, because they are created by the ReplicaSet named javawebapprs.

The ending parts -abc12 and -def34 are random unique strings automatically generated by Kubernetes.

This ensures Pod names never clash, even if created by the same ReplicaSet.

So both Pods belong to the same ReplicaSet, but they get different suffixes.

(2) Pod Deletion & Auto-Healing
1. Check Pods Before Delete
kubectl get pods

NAME                    READY   STATUS    RESTARTS   AGE
javawebapprs-abc12      1/1     Running   0          2m
javawebapprs-def34      1/1     Running   0          2m

2. Delete One Pod
kubectl delete pod javawebapprs-abc12

pod "javawebapprs-abc12" deleted

3. After Few Seconds (ReplicaSet creates a new Pod with random name)
kubectl get pods

NAME                    READY   STATUS    RESTARTS   AGE
javawebapprs-def34      1/1     Running   0          2m
javawebapprs-dpkn2      1/1     Running   0          5s


Explanation in simple words:

ReplicaSet always maintains DESIRED = 2 Pods.

When you delete one Pod (javawebapprs-abc12), RS notices only 1 Pod is left.

ReplicaSet notices Pod count dropped creates a new Pod.

So it immediately creates a new Pod (javawebapprs-dpkn2) with a new random suffix.

(3) Check Pod Ownership
kubectl describe pod <pod-name>


or

kubectl describe pod <pod-name> | grep -i "Controlled By"


Output:

Controlled By:  ReplicaSet/javawebapprs

8. ReplicaSet Update with New Image Version
1. Initial Setup

You deployed a ReplicaSet (RS) with image version 1.0.0.

RS created 2 Pods based on that template.

Everything was running fine.

2. Update Attempt Change Image to 1.0.1

Edit rs.yaml:

containers:
- name: javawebapp
  image: kkeducation12345/spring-app:1.0.1


Apply the updated ReplicaSet:

kubectl apply -f rs.yaml

replicaset.apps/javawebapprs configured


The RS configuration in etcd (Kubernetes’ internal store) was updated.

3. Check Pods Again
kubectl get pods


Still the same old Pods are running.

No new Pods are created because the ReplicaSet only ensures the number of Pod = 2, It does not restart existing Pods when you change the template.

NAME                    READY   STATUS    RESTARTS   AGE
javawebapprs-dpkn2      1/1     Running   0          5m
javawebapprs-def34      1/1     Running   0          7m

4. Verify Pod Image

Check one of the running Pods:

kubectl describe pod javawebapprs-def34


Even though we updated the ReplicaSet YAML to 1.0.1, the running Pod still shows Image: 1.0.0.

ReplicaSet does not replace or restart old Pods.

It only makes sure the count of Pods matches.

5. Why Didn’t the Pods Update?

ReplicaSet is designed to maintain a fixed number of Pods matching its template. However:

It does not track changes to the Pod template (like image updates).

If the number of Pods is already correct, RS does nothing even if the template has changed.

So, your Pods continue running with the old image (1.0.0), even though the RS now says 1.0.1.

RS is not meant for rolling updates or version management.

9. How to Update Pods in a ReplicaSet

If you want, you can scale the ReplicaSet (increase replicas) → the new Pods created will come with the new version of the image.

But for updating existing Pods, you must delete the old Pods manually, or delete and re-apply the ReplicaSet YAML with the new version.

For automatic updates and smooth version rollout always use a Deployment instead of a plain ReplicaSet.

10. Summary

ReplicaSet = modern replacement for ReplicationController.

Maintains the desired number of Pods at all times.

Works by comparing desired vs observed state in a control loop.

Uses label selectors (matchLabels + matchExpressions) to manage Pods.

Provides self-healing, scaling, adoption of orphan Pods.

In real-world production always managed via Deployments.
