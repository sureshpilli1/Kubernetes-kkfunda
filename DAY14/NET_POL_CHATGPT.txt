Network Policies
--> Network Policies in Kubernetes are used to control the communication between pods and   external endpoints. 
--> They are a way to define rules that govern how pods can connect to each other and to other network endpoints. 
--> This can enhance the security of your applications by restricting access and ensuring that only authorized traffic is allowed.

Key Concepts of Network Policies
Namespaces: Network Policies are applied within a specific namespace. You can create different policies for different namespaces.
Selectors: Network Policies use selectors to define the pods they apply to:
Pod Selector: Specifies which pods the policy affects.
Namespace Selector: Specifies which namespaces the policy can affect.

Types of Rules:
	Ingress Rules: Control incoming traffic to the selected pods.
	Egress Rules: Control outgoing traffic from the selected pods.
Policy Types: Each Network Policy can specify rules for ingress, egress, or both.

1. What is a NetworkPolicy?
A NetworkPolicy is:
A Kubernetes resource that controls traffic (ingress/egress) to Pods
Simple idea
Without NetworkPolicy → Everything can talk to everything 
With NetworkPolicy    → Only allowed traffic is permitted

2. Important prerequisite (very important)
NetworkPolicies work only if your CNI supports it
Examples:

3. Types of traffic control
Ingress

Egress
Outgoing traffic from Pod

apiVersion: networking.k8s.io/v1

  name: example
  namespace: prod

  podSelector:
    matchLabels:
      app: mongodb

  policyTypes:
  - Ingress
  - Egress

Pod labels (NOT Services, NOT Deployments)

If NetworkPolicy exists:
Only defined traffic is allowed

I am confused between pod selector in specification and pod selector in ingress and another question is ingress has pod selector and name space selector why egress didn't have them
1. spec.podSelector — WHO is protected?
You have:
spec:
  podSelector:
    matchLabels:
      app: springapp
This answers:
"Which Pods should this NetworkPolicy control?"
So Kubernetes looks in the prod namespace and finds:
prod namespace

Pod 1: app=springapp     ← selected ✅
Pod 2: app=frontend      ← not selected
Pod 3: app=database      ← not selected
Pod 4: app=springapp     ← selected ✅
spec.podSelector = WHO is being protected by this policy.

2. ingress.podSelector — WHO can connect to them?
Now look at:
ingress:
- from:
  - podSelector:
      matchLabels:
        role: frontend
This has a completely different purpose.
It asks:
"Which Pods are allowed to SEND traffic to my protected Pods?"
So imagine:
frontend Pod
role=frontend
      │
      │  TCP :6379
      ↓
springapp Pod
app=springapp
The ingress.podSelector selects the source Pods, not the destination Pods.

spec.podSelector	Which Pods does this policy protect?
ingress.podSelector	Which Pods can send traffic into those protected Pods?

3. Why does ingress have podSelector AND namespaceSelector?
Because Kubernetes may need to identify the source in different ways.
Your policy says:
ingress:
- from:
  - ipBlock:
      cidr: 172.17.0.0/16

  - namespaceSelector:
      matchLabels:
        project: myproject

  - podSelector:
      matchLabels:
        role: frontend
This gives three possible ways of identifying an allowed source.
A. ipBlock
ipBlock:
  cidr: 172.17.0.0/16
Means:
Allow traffic from these IP addresses.

B. namespaceSelector
namespaceSelector:
  matchLabels:
    project: myproject
Means:
Allow traffic from Pods belonging to namespaces with project=myproject.

C. podSelector
podSelector:
  matchLabels:
    role: frontend
Means:
Allow traffic from Pods having role=frontend.
In this particular policy, because the podSelector is alone in that from item, it selects matching Pods in the same namespace as the NetworkPolicy (prod).

4. Now your second question: Why doesn't egress have namespaceSelector or podSelector?
Actually, egress CAN have them.
There is nothing about Kubernetes that says:
ingress can have podSelector, but egress cannot.
Both ingress and egress support:
ipBlock
namespaceSelector
podSelector
Your example simply chose to use only ipBlock for egress.
Your egress is:
egress:
- to:
  - ipBlock:
      cidr: 10.0.0.0/24

  ports:
  - protocol: TCP
    port: 5978

5. Egress can also use namespaceSelector
For example:
egress:
- to:
  - namespaceSelector:
      matchLabels:
        project: database
  ports:
  - protocol: TCP
    port: 27017
Meaning:
The springapp Pod can send TCP traffic on port 27017 to Pods in namespaces labeled project=database.

6. This gives us a very useful pattern
Think about NetworkPolicy like this:
                 NETWORK POLICY
                       │
              ┌────────┴────────┐
              │                 │
           INGRESS             EGRESS
              │                 │
          incoming             outgoing
              │                 │
           from:                to:
              │                 │
       ┌──────┼──────┐    ┌─────┼──────┐
       │      │      │    │     │      │
      Pod   NS     IP    Pod   NS     IP
Where:
Ingress
from:
  podSelector
  namespaceSelector
  ipBlock
means:
Who can come IN?

Egress
to:
  podSelector
  namespaceSelector
  ipBlock
means:
Where can I go OUT?
