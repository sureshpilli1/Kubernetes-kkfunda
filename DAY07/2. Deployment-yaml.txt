BLOG NOTES:
1. Introduction
Kubernetes has changed the way we run and manage container-based applications. 
One of its most important features is the Deployment object. 
A Deployment takes care of creating and managing Pods for you, so your app is always available, scalable, and easy to update.
Instead of manually starting or stopping Pods, you just tell Kubernetes what you want (the desired state), 
and the Deployment makes it happen. Whether you need to release a new version or handle more traffic, Deployments make the process smooth and automatic.

2. What is a Deployment?
Deployments are the backbone of Kubernetes applications.
They manage the lifecycle of Pods and provide features like scaling, rolling updates, and rollback.
When you define and use a Deployment:
The Deployment automatically creates a ReplicaSet in the background.
ReplicaSet Management
The ReplicaSet ensures that the desired number of Pods are running at all times.
The ReplicaSet creates and manages Pods.
Inside each Pod, there can be one or more containers running your application.
Flow: Deployment → ReplicaSets (RS) → Pods → Containers
Self-Healing in Deployments
Kubernetes automatically replaces failed or unhealthy Pods to maintain the desired state.
The controllerManager constantly watches the Pods and recreates them if they fail.
Once the Kubernetes Deployment is set up, the only manual task is updating the configuration 
(such as changing the container image version or adjusting replica counts).
After that, Kubernetes handles everything else automatically:
It will roll out the update by gradually replacing old Pods with new ones.
If an update causes issues, Kubernetes can automatically roll back to the previous version without manual intervention.

3. Key Features of Deployments:
Replica Management → Ensures the specified number of Pods are always running.
Rolling Updates → Updates applications gradually with minimal or no downtime.
Rollback Capability → Easily revert to a previous version if a rollout fails.
Declarative Scaling → Adjust the number of replicas by changing a single field in the YAML.

4. Deployment Strategies in Kubernetes
When you release a new version of your application, Kubernetes provides different strategies to control how Pods are updated. 
The two main strategies are Recreate and RollingUpdate.
1. Recreate Strategy
In this strategy, all the old Pods are terminated first, and then new Pods are created with the updated version.
This means there will be downtime during the update because, for a short period, no Pods are available to serve requests.
When to use Recreate?
When downtime is acceptable.
When running two versions of the app at the same time could cause conflicts (for example, database schema changes).
Example flow:
Step 1: Existing Pods → [v1][v1][v1]
Step 2: Delete all Pods
Step 3: Start new Pods → [v2][v2][v2]
Let’s see the example:

2. RollingUpdate Strategy (Default)
In this strategy, Pods are updated gradually, one by one (or in small batches).
At any time, some old Pods keep running while new Pods are being created.
This ensures minimal or zero downtime.
When to use RollingUpdate?
When the application must be available 24/7.
When it’s safe for old and new versions to run together during the rollout.
Example flow:
Step 1: Existing Pods → [v1][v1][v1]
Step 2: Replace one Pod → [v2][v1][v1]
Step 3: Replace second Pod → [v2][v2][v1]
Step 4: Replace third Pod → [v2][v2][v2]

      app: javawebapp

      name: javawebapp

        app: javawebapp

You will see old Pods still running
New Pods start creating
Status may show: ContainerCreating, Running, or sometimes Error (like image pull issues).
Old Pods Terminating, New Pods Running
After a few seconds, new Pods reach Running state.
At the same time, old Pods go into Terminating state.
This is Kubernetes’ RollingUpdate strategy:
Don’t stop all Pods at once.
Gradually replace Pods to keep the service available without downtime.

2. Final State
Old ReplicaSet → scaled down → Pods count = 0.
New ReplicaSet → scaled up → Pods count = 3.
Now, only the new version Pods are running.

3. Why RollingUpdate is Preferred
No downtime → Users never notice the upgrade because at least one Pod is always running.
Safer upgrades → New Pods are created step by step. If a Pod fails, the update stops before all old Pods are removed.
Easy rollback → If there’s an issue, Kubernetes can quickly roll back to the previous ReplicaSet.
Production standard → In real-world clusters, RollingUpdate is the default choice because it ensures high availability and smooth transitions.








# Scale a deployment
kubectl scale deployment <DEPLOYMENT_NAME> --replicas=<NUMBER_OF_REPLICAS>

# Check rollout status
kubectl rollout status deployment nginx-deployment

# Get all deployments
kubectl get deployment

# Update image and record the change
kubectl set image deployment nginx-deployment nginx-container=nginx:latest --record

# Check associated ReplicaSets
kubectl get replicaset

# Show rollout history
kubectl rollout history deployment nginx-deployment

# Show details of a specific revision
kubectl rollout history deployment nginx-deployment --revision=1

# Rollback to specific revision
kubectl rollout undo deployment nginx-deployment --to-revision=1
